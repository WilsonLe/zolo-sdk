# Personal-account web protocol

The SDK uses a locally patched Zalo Web transport from `zca-js` 2.2.0. The [local patch provenance](../vendor/README.md) and [cookie guide](cookie-scope.md) describe the HTTP corrections, per-connection WebSocket cookie selection and remaining boundaries. Normal requests now reject automatic redirects and visible origin changes strip caller credentials; prior live sign-in results do not verify this changed policy. The npm tarball and the `v2.2.0` Git tag identify the same source commit, `dadfef18bcac53537741855c99f084152da1fad9`. Zalo's developer portal describes Zalo Social as a sign-in product and Zalo Official Account as the OpenAPI messaging product. The personal-account web transport has its own endpoints and session lifecycle. ## Login and session resume

1. The upstream client loads the login page with a fresh cookie jar and reads the version from the `main-<version>.js` script URL. It calls `/account/logininfo`, `/account/verify-client`, and `/account/authen/qr/generate` on `id.zalo.me`.
2. The login code becomes a PNG for the account owner to scan in Zalo. Upstream long-polls `/account/authen/qr/waiting-scan` and then `/account/authen/qr/waiting-confirm`. When the owner accepts the login, upstream checks the resulting session through `/account/checksession` and the `jr.chat.zalo.me/jr/userinfo` endpoint.
3. QR login produces a reusable credential bundle consisting of cookies, an installation identifier that upstream calls `imei`, and a user agent. The identifier is generated for the SDK installation from a random UUID and a user-agent hash. Resume creates a fresh SDK session from this credential bundle and repeats the chat bootstrap. The upstream `GotLoginInfo` callback fires before the chat bootstrap, so persist the credentials after the overall login resolves. [QR transport](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/loginQR.ts) · [Login wrapper](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/zalo.ts) · [Identifier generation](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/utils.ts#L720-L722)

The chat bootstrap calls `wpa.chat.zalo.me/api/login/getLoginInfo` and `getServerInfo`. Upstream signs the bootstrap parameters and uses an encrypted login envelope. The returned context supplies the user ID, HTTP session key, service map, WebSocket endpoints, and feature settings. Normal operations select hosts from the service map. Many send JSON encrypted as a base64 `params` value in the query or form body and resolve an encrypted response envelope. Preserve returned identifiers as strings when building SDK integrations. [Chat bootstrap](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/login.ts) · [Request and encryption helpers](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/utils.ts)

## Web sign-out

`PersonalZalo.submitWebSignOut(api, signal?)` performs the two form requests used by the Web login widget. It first posts `continue=https://chat.zalo.me/` to `/jr/logout-token` on `id.zalo.me`, then posts the returned token to `/account/logout` on the same origin. The SDK uses cookies scoped to each request URL, applies token-step cookie updates in an isolated jar, and leaves redirect navigation to the application. The response contains only the submission status and HTTP code. Verify revocation independently before treating a submission as confirmed. After a transport failure during form submission, the SDK returns `submission-unknown` because the server may already have received the form. `clearLocalSession()` separately clears the configured local store.

The Web startup bundle selects `ZaloLoginWidget.getTokenLogout()` at byte 9,347,147 and `logoutWithToken()` at 9,347,866. The referenced widget asset has SHA-256 `b67896103b82aeaddd97260cb8eacc438293448c447397978d30565c8413b15b`. Its token and form builders begin around bytes 7,047 and 9,840. Fixture coverage includes both form requests, cookie scope, cancellation, token rejection, redirect isolation, and ambiguous submission. Server revocation remains unverified. ## Operations and realtime events

The pinned API declares 155 callable properties. The list includes protocol utilities such as `custom`, `getCookie`, and `getContext`, alongside account operations. `getCookie`, `getContext`, and the listener's `cipher_key` event expose session secrets. The published declaration is the exact upstream inventory. [API declaration](https://cdn.jsdelivr.net/npm/zca-js@2.2.0/dist/apis.d.ts) · [API construction and method bindings](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis.ts)

| Area | Representative operations in the pinned upstream release |
| --- | --- |
| Messages | Send text, quoted messages, styled text, mentions, attachments, video, voice, stickers, cards, and links. Forward, recall, delete, react, and send delivery, seen, or typing signals. |
| Friends and profiles | List friends, find users, query profiles, manage friend requests and aliases, block users, and update profile and avatar. |
| Groups | List and create groups, inspect members and group history, manage pending and blocked members, invite, manage group links and roles, edit settings, and leave or disband groups. |
| Conversation controls | Mute, archive, pin, hide, mark unread, set automatic deletion, and manage labels. |
| Extended features | Manage reminders, notes, polls, quick messages, auto replies, catalogs and products, and saved bank-card information. Availability may depend on account and group permissions. |

WebSocket events have a four-byte header (version byte, little-endian command, subcommand byte) followed by a JSON body. The upstream decoder handles plain JSON and envelopes that use Base64, deflate, or AES-GCM with a connection key. Message commands `501` and `521` carry direct and group messages, `601` carries control events, and `612` carries reactions. The client also emits history, read and delivery receipts, typing, upload completion, and friend and group events. Wait for the connection before requesting history. `requestOldMessages` takes a thread type and cursor rather than a conversation ID. `getGroupChatHistory` is the group-specific HTTP operation. [WebSocket listener and commands](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/listen.ts) · [Envelope decoder](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/utils.ts#L380-L418) · [Group history](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/getGroupChatHistory.ts)

Register a listener `error` handler before starting it. Upstream documents a single web listener per account. A second browser or SDK WebSocket can displace the first. The SDK's upstream `retryOnClose` schedules reconnects with timers outside `stop()`'s cancellation path. Uploads that wait for `file_done` need an active WebSocket, and local image paths require an `imageMetadataGetter` in v2. [Upstream listener notes and image metadata example](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/README.md) · [Attachment upload implementation](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/uploadAttachment.ts)

The upstream inventory gives a finite implementation target. Voice and video calls, Signal-based conversation keys, desktop-local archives, and a complete per-conversation direct-message history API remain outside that inventory. Presence of service-map keys such as `voice_call`, `chat_e2e`, and `group_e2e` supplies leads for separate protocol work.
