# E2EE delivery and seen receipts

`sendE2eeDeliveryReceipts(api, input)` explicitly reports delivery for up to 50 decrypted messages. Set `seen: true` to include seen status. Use the received message's exact sender, destination, message and client message IDs, message type, and sender platform. Keep large numeric identifiers as decimal strings.

The installed client sends direct delivery through `POST /api/e2ee/pc/t/message/delivered` on `chat_e2e` (internal command 16200) and group delivery through `POST /api/e2ee/pc/t/group/delivered` on `group_e2e` (16203). Account AES protects `{msgInfos: JSON.stringify({seen,data,grid?})}`. Each row uses `cmi` for the client message ID, `gmi` for the message ID, `si` and `di` for sender and destination, `mt` for message type, and `fDI` for the sender platform. Optional status, action, command, and timestamp fields use `st`, `at`, `cmd`, and `ts` and default to `-1`. `rGmi` holds the original message ID when present.

Socket commands `553` and `554` push direct and group receipt records under `data.delivereds`. `extractE2eeReceiptEvents(frame)` reads those pushes and supplied offline frames `518` and `519`. The rows can describe seen status, delivery, or decryption failure. Inspect `decryptionError` before treating a row as a delivery. A nonzero value represents a decryption failure. The shipped code also declares standalone encrypted `/seen` HTTP routes. The SDK uses the combined seen flag from the observed delivery path.

After processing and persisting offline receipts, call `control.deleteOfflineReceipts(events)` with up to five original extractor results of one queue type from the account's feed. It uses socket command `557` for direct and `558` for group with version 1, subcommand 1, and `{reqId,data:{delivereds:[...]}}`. It removes server queue records and correlates the reply by `data.reqId`. Receipt rows are replayed in their decoded provider form. Online pushes remain available for inspection. The shipped client uses a separate online cleanup path for decryption failures.

`requestE2eeOfflinePage()` uses the receipt-specific request mode for announced commands 518 and 519. Both the first fetch and continuation send numeric `lastId: 1` and `preIds: []`. When `page.next` is available, persist and delete the current receipts before requesting that continuation. The pager leaves processing and deletion to the caller. The [installed SHARED member](desktop-evidence.md) records receipt commands and the five-row deletion cap at bytes 3,270,030 and 3,278,001, incoming receipt routing at 5,303,831 and 12,592,402, HTTP endpoints at 12,433,097 and 12,433,321, outgoing row construction and 50-row limit at 16,167,605–16,168,695, and offline deletion at 12,590,740 and 14,416,524. The Web startup bundle independently contains the same HTTP builders and socket cleanup. Local fixtures verify the encrypted request shapes and decoded receipt handling. Live delivery and deletion remain unverified.
